# P4：Policy 路线与按角色分配 GPU
branch: feat/p4-policy · status: in_progress · updated: 2026-11-04

## Goal

design §9.4 / §9.13 P4：一个 trial 里仿真器与模型服务各自要卡，且必须一起满足才启动；首个落地 benchmark 是
vla-eval（LIBERO），仿真跑在其原版镜像的 `--no-docker` 直接入口里，模型服务作为 Orbit service。

## Changes

- **按角色分配**（`resources/allocate.ts` `allocateRoles`）：`RunSpec` 的 `main` 与带 `role` 的 service 各自声明
  `gpus / gpuMemGB`；一次整组分配，角色之间不共享卡；任一角色不满足就整体排队（不会出现"一半拿着 GPU 等另一半"）。
  `Lease.roles` 记录每个角色的卡、CPU、内存；单容器 Run 与旧租约仍用扁平的 `gpuIds`。
- **service 用 GPU**：`ServiceSpec` 增加 `role`、`gpus`、`gpuMemGB`、`gpuFeatures`；服务容器拿到自己角色的卡
  （`serviceContainer` 之前硬编码 `gpuIds: []`）。接口约束：带 role 的服务不能用 process 后端、不能配宿主路径挂载、
  不能与 host 网络同用、无 role 的服务不能申请 GPU。
- **Run 自己的容器**只拿 `main` 角色的卡（`launch.mainGpus`），GPU 映射核对也按 main 角色比对。
- `leaseRequest` 把 roles 的 GPU 计入总数（CPU/内存照旧累加），preflight / placement / 远端放置都改走 `allocateRoles`。
- **vla-eval 外部适配器**（`examples/bench-adapters/vla-eval/`）：
  - `tasks` 在 benchmark 镜像内真实枚举（`LIBEROBenchmark.get_tasks()`），任务 id 为 `<suite>:<任务名>`；
  - solve 用原版 `vla-eval run --no-docker`（镜像自身的入口环境），一个 trial 一个任务、`episodes_per_task` 个 episode；
  - `empty` 方法：镜像内跑 `zero_policy.py`（零动作策略，`role: policy`，0 GPU），测得 benchmark 的真实下限；
  - `external` 方法：`entrypoint` 是模型服务镜像，`config` 给 `command`/`gpus`，作为 `role: policy` 的服务并拿到整卡；
  - verify 读回 `aggregate.json` 并重算 success（`check.py`），与 solve 一致才算有效；
  - 声明 `official`：vla-eval 把 episode error 计入分母（`errors: fail`, `unit: sample`）。
- 文档：design §9.4（已写策略）、本记录；`docs/status.md`。

## 调试记录（真实运行发现的问题，均已修）

1. 适配器 spec 带宿主挂载时被"带 role 的服务不能挂宿主路径"拒绝——该约束多余，改为只要求 docker 后端。
2. service 的 `mounts` 字段不存在（是 `binds`）；写错会被 schema 静默丢弃，服务里看不到文件。已改为 `binds`。
3. 镜像 ENTRYPOINT 是 `conda run -n libero vla-eval`，列表形式的 command 会被当作它的子命令。核心新增
   `RunSpec.entrypoint` / `ServiceSpec.entrypoint`（对应 `docker run --entrypoint`），vla-eval 用
   `/opt/conda/bin/conda run … vla-eval run …` 与原版一致。
4. LIBERO 读 `~/.libero/config.yaml`；Orbit 以宿主用户运行读不到镜像的 `/root/.libero`。solve 与 verify 用
   `root: true`（与 Harbor 运行任务容器一致）。
5. 评分文件：vla-eval 写 `<Benchmark>_aggregate.json`；score 与 verify 都要读它，曾经一边读
   `vla-eval-summary.json`、另一边少一个字段，导致"verifier 与保存结果不一致"。现两边共用同一份字段集。

## Next / open issues

1. `gpuFeatures`（例如要求 RTX）目前只出现在排队原因里，尚未按卡型过滤。
2. 真实 VLA 权重未下载；external 方法的完整链路只有协议与服务层验证。
3. vla-eval 一个 trial 只跑一个任务；`episodes_per_task > 1` 时是同一任务的多个 episode，与上游 `mean_success` 一致。
