## Goal

子任务 B 已经让 Claude Code 通过 `orbit-computer`（CLI + MCP）操作 BrowserGym/MiniWoB，证据由可信 service 签名。
P6 主线要把它从"一个 benchmark 的特例"变成"Orbit 的通用能力"，并补齐 design §9.13 P6 的验收：
**Claude Code 在 MiniWoB / 第二个 GUI 后端与 EFE CPU 任务跑通，并有统一轨迹。**

四件事，按顺序做（每件一个提交）：

1. **GUI service 通用化**：把 BrowserGym `server.py` 里与后端无关的部分（单 episode、动作 id 幂等、步数预算、finish、
   证据布局、哈希与 Ed25519 签名）抽成共享模块，BrowserGym 成为第一个后端；接入第二个后端 **CUA-Lite MiniWoB**
   （已校准、纯 CPU），让 CLI Agent 也能在 CUA-Lite 上跑。
2. **MCP 由 Orbit 接线**：现在 adapter 只在指令里提示"支持 MCP 时可用"，Agent 实际拿不到 MCP 配置。
   让 adapter 声明工具，Orbit 按 Agent 定义把 MCP server 写进该 Agent 的配置；不支持的 Agent 只用 CLI。
3. **CLI Agent 模型故障的结构化识别**（子任务 B 遗留）：认证拒绝 / 连接失败时 Agent 没有动作，结束 hook 仍留下完整的
   noop 证据，目前可能被当作有效 0 分。按可信、脱敏的 transcript 证据判 `model_unavailable`（invalid）。
4. **EFE × coding agent + 统一轨迹**：Claude Code 跑 EFE MetaWorld+ standard（P3 已用 oracle/empty 校准的那个任务），
   并把 Agent 会话与 EFE 环境记录合成一份 trial 轨迹（design §9.8 的最小可用版本）。

不做：OSWorld / MobileWorld 的 CLI 桥（需要 KVM 真实校准，留 P7 或单独任务）；allowlist 网络（仍按偏差运行）；
浏览器回放与状态恢复；Codex GUI（见第 3 节"Codex"一条，只做诊断）。

## 设计（按此实现；有更好方案先写进本文）

### 1. 共享 GUI service 与第二个后端

- 新目录 `examples/tools/orbit-gui-service/`：
  - `service.py`：通用 HTTP 层与 episode 状态机（现 `server.py` 的通用部分原样移来，**行为不变**）。
    后端接口是一个 Python 类：`spec() -> dict`、`reset() -> obs`、`step(action:str) -> (obs, reward, terminated, truncated, info)`、
    `close()`；`obs` 至少含 `screenshot: bytes`、`goal`、可选 `text`（a11y 树等）。service 负责步数、id 去重、finish、证据。
  - `evidence.py`：哈希 + 签名 + `validate`（从 browsergym 移来；browsergym 保留同名薄包装或改为导入，两个 adapter 的
    verify 都挂这一份）。证据格式（`plan.json / trajectory.jsonl / screenshots/ / result.json / evidence-signature.json /
    trajectory-review.json`）不变，旧 trial 的 rescore 必须仍然通过。
- BrowserGym：`server.py` 变成"BrowserGym 后端 + 调用共享 service"；`orbit-computer` 不改协议。
- CUA-Lite：新增 `cli` 方法（只对已校准的 MiniWoB 子集开放；WebVoyager / Online-Mind2Web 对 `cli` 报 unsupported 并写原因）。
  - 后端用 CUA-Lite 自己的环境封装，**动作语言取 CUA-Lite canonical tool call**（design §9.5：坐标 `[0,1000]`、computer 族、
    finish），`/spec` 给出它的原版动作说明——不要把 BrowserGym 的动作字符串套给 CUA-Lite，评测条件以各自上游为准。
  - 声明 `requires: ["gui"]`，conditions 写明"CLI Agent 经 Orbit GUI service；观测仅截图"。
  - 镜像沿用 A 线的固定 digest；服务端依赖若缺（如 openssl），在 A 线 Dockerfile 里补并 bump 标签。
- 工具挂载约定（两个 adapter 一致）：`/usr/local/bin/orbit-computer`；`ORBIT_GUI_URL`；service 名 `gui`；
  `gui` 网络 internal，main 同时接 default（模型网络）与 `gui`。

### 2. MCP 由 Orbit 接线

- 契约（`contracts/adapter.ts`）：`agentTask` 增加可选
  `tools?: { name, command: string[], env?: Record<string,string> }[]`（≤ 8 个；`name` 为 `[a-z0-9-]+`）。
  只是"Agent 可用的 MCP stdio server"，**不**是 Orbit 执行的命令；adapter 不能借它设置 Orbit 自管字段。
- 契约（`contracts/agent.ts`）：`AgentCommand` 增加可选 `mcp`：
  `{ kind: "claude-json", flag: string } | { kind: "codex-toml" } | { kind: "none" }`（默认 none）。
  - `claude-json`：Orbit 在 Agent home 写 `orbit-mcp.json`（`{"mcpServers": {name: {command, args, env}}}`），并在 argv 中
    `{instruction}` 之前插入 `flag <path>`（claude-code 为 `--mcp-config`）。
  - `codex-toml`：在 Agent home 的 `config.toml` 追加 `[mcp_servers.<name>]`（`command`、`args`、`env`）；已有同名表时报错，
    不覆盖用户配置。
  - 内置定义：claude-code → `claude-json`；codex → `codex-toml`；其余保持 none（`capabilities.mcp` 为 true 但没接线的，
    在 `orbit agent show` 中提示"MCP declared, not wired"）。
- 渲染位置：`bench/protocol.ts` `toRunSpec` 处理 `agentTask` 时，与生成 Agent 命令同一处做；`requires` 含 `mcp` 的
  benchmark，`mcp.kind === "none"` 的 Agent 在提交时拒绝（复用 `checkMethod` 的 `requires` 检查，不新增路径）。
- BrowserGym / CUA-Lite 的 `cli` solve 声明 `tools: [{ name: "orbit-computer", command: ["orbit-computer", "mcp"] }]`；
  指令模板改为"可用 CLI 或 MCP 工具 orbit-computer"，固定模板写入 conditions。MCP 是否被实际使用记录在 trial 的
  review details（从 transcript 的 tool_call 名称判断），**不**影响有效性。

### 3. 模型故障识别

- 在 `harness/index.ts` 的 transcript 分类中补齐两类实测模式（以真实 transcript 为准，写成测试 fixture，脱敏）：
  认证拒绝（invalid api key / 401 / `authentication_error` / codex `Unauthorized`）与连接失败
  （`ECONNREFUSED` / `fetch failed` / `stream disconnected` 在**没有任何成功模型响应**时）。
- 判定规则写清楚：**只有**"transcript 中没有成功的模型回复，且最后的错误属于上述类别"才判 `model_unavailable`；
  有过成功回复后才失败、或 Agent 自己选择结束的，按正常结果评分。不能用"退出码非 0 且没有动作"代替识别。
- `agentFailureIssue` 已在 `classify.ts` 接入；确认 adapter（external 协议）的 `agentTask` 路径也会解析 transcript
  （BrowserGym cli 的真实 trial 上验证），没有就补上。
- **Codex**：子任务 B 中 Codex 的 GUI 模型连接失败。只做诊断：用一个最小非 GUI 任务确认 Codex 认证/网络在 bench 路径可用，
  再跑一个 MiniWoB 任务；成功则把 codex 的 `capabilities.gui` 改为 true 并记 passed，否则记 failed 与原因，保持 false。

### 4. EFE × Claude Code 与统一轨迹

- 用 P3 的登记方式（`-c allowlistNetwork=public`，偏差照记）在 MetaWorld+ `metaworldplus-assembly-i00-standard` 上跑
  `claude-code`：Harbor 路径已经支持 CLI Agent 的 `agentTask`，预期不需要改 adapter；遇到缺口按 §9.6 第 0 条先列清单再补核心。
- 统一轨迹（design §9.8 的最小版本，**不**做全量 events.jsonl 体系）：
  - 新纯函数 `packages/orbit/src/bench/trajectory.ts`：输入 solve Run 的 Agent transcript（已有解析器产出的
    `SessionMessage[]`）与 EFE 产物（journal / 视频 / reward），输出现有 `EpisodeTrajectory`（`contracts/trajectory.ts`）+
    会话消息引用；导入器各自带 fixture 测试。完整度标注（会话完整 / 只有环境记录 / 截断）放在 `EpisodeTrajectory` 的可选字段
    `completeness`（契约改动 → daemon、client、Web 与测试同步）。
  - 生成时机：trial 打分后由 daemon 写入 solve 输出的 `orbit-trajectory.json`，review 加一项 `kind: "episode"`；
    失败不影响分数与有效性，只记 issue。
  - BrowserGym / CUA-Lite 继续用 GUI trajectory；不强行合并两种视图。

- 真实模型调用只用用户已配置的 auth profile；transcript fixture 必须脱敏，密钥与原始会话不进仓库。
